# Changes to MGPU Bridge in `bridge/`

Upstream: MGPU Bridge @ `4f0cf56` (see `bridge/UPSTREAM.md`). Every change is tagged `NRB<n>`
in code comments and log lines (`[MGPU][NRB<n>]`), so `grep NRB` finds all of them.
Version string: `0.3.0-discovery-lat+nrb.1`.

The game itself also needs sl-standin (our `sl.interposer.dll`, which also loads nvapi-gate first) and nvapi-gate on this rig - see
`rt-init-error.md`. `tools/deploy.ps1` installs both together with the add-on.

| Tag | Where | What and why |
|---|---|---|
| NRB1 | `gpu1_context.cpp` `ngx_load_core()`, used by the startup probe and `stream_nr_create` | Load `_nvngx.dll` from `HKLM\SOFTWARE\NVIDIA Corporation\Global\NGXCore\FullPath` when it is not already resident. A game on AMD never loads NGX, and the driver store is not on the loader path, so upstream's bare-name `LoadLibraryW` fails. Proven with `tools/nr-probe`. |
| NRB2 | `gpu1_context.cpp` `stream_nr_create` | When core `Init` returned `FAIL_OutOfDate` and `GetCapabilityParameters` then fails, log a plain "quit and relaunch the game" error. Before NRB11 that happened on ~half of launches, and an in-process retry never recovered (5 tries over 5 s). The message now says it should not happen with NRB11 and asks for the log. |
| NRB3 | `nrb_vendor.hpp`; `dllmain.cpp` calibrator install; `gpu1_context.cpp` Reflex | Skip the NGX calibrator (import-table patching) and Reflex (NvAPI on the game device, including `clear_residue`) when the game's GPU is not NVIDIA. Logged once each. |
| NRB4 | `worker.cpp`, `gpu1_context.cpp` `startup_probes_enabled()` | The startup NGX probe and transit probe (which opens a second device on the game's GPU while the game initialises) are opt-in: `StartupProbes=1`. Default off. |
| NRB5 | `adapter.cpp` `add_hidden_adapters()` | After `EnumAdapters1`, list hardware adapters through DXCore and open any missing one with `EnumAdapterByLuid`. RTInitFix hides NVIDIA from every DXGI factory in the process (vtable patch), which otherwise leaves the bridge with no neural GPU. sl-standin hides it from game-side callers only, so this matters now only with `deploy.ps1 -UseRTInitFix`. Links `dxcore.lib`. |
| NRB7 | *removed* | Logged whether the NVIDIA App / overlay was running before NGX Init and named it in the NRB2 error; `tools/launch.ps1` closed both and could restart the NVIDIA display service. All based on a wrong theory of the intermittent `FAIL_OutOfDate` (the cause was NRB11). Removed in the cleanup of 2026-10-07, with `nrb_nvapp.hpp`. |
| NRB8 | `adapter.cpp` `drop_duplicate_gpus()` | Run11 listed the RTX 5070 twice in DXGI (two LUIDs) and rule 4 refused to choose. When two hardware entries match on vendor, device, subsystem, revision and VRAM, keep the one DXCore lists and drop the other; if DXCore lists both or neither, keep both. |
| NRB9 | `nrb_ffx_tap.cpp/.hpp`; `dllmain.cpp` `on_present` | Phase 4.2 FFX tap (observe only). FSR 3.0 path: patches the import slots of `ffxFsr3UpscalerContextCreate/Dispatch/Destroy` (ffx_fsr3upscaler_x64.dll) in every module, by value. FFX API path (FSR 3.1, and FSR 4 through it): inline hooks on `ffxCreateContext/ffxDispatch/ffxDestroyContext` in amd_fidelityfx_dx12.dll, installed only if the prologue bytes match build 1.0.1.41314. Logs the upscale inputs once per second; `nrb::ffx::latest()` exposes them for 4.3. `FfxTap=0` turns it off. |
| NRB10 | `nrb_ffx_tap.cpp` `copy_motion_vectors`; `dllmain.cpp` finish_effects; `gpu1_context.cpp` arm | Phase 4.3a: FSR's motion vectors into the MVec lane. Inside the upscale dispatch, once per present: barrier to COPY_SOURCE from the state FSR declared, `stream_mvec_copy`, barrier back (the calibrator's evaluate-route pattern). Every frame `probe::set_mvec_override` gets FSR's MV resource so the MVec=3 arm hold sees a stable handle. At arm, `MVecScaleX/Y` are multiplied by FSR's motionVectorScale. `FfxMvec=0` turns the copy off. |
| NRB11 | `gpu1_context.cpp` `ngx_pf_init_core`, both core `Init` calls; `tools/nr-probe` | Root cause of the intermittent `FAIL_OutOfDate`. The driver's `NVSDK_NGX_D3D12_Init` (disassembled, 617.14) takes `(AppId, DataPath, Device, SDKVersion)` and fails if the 4th argument is > 0x15; we (and upstream) called a 5-argument form with `&FeatureCommonInfo` 4th, so a stack address was compared as the version and passed only when ASLR set its bit 31. Core Init is now called with 4 arguments. The snippet's own Init (startup probe only, off by default) is unchanged. |
| NRB12 | `gpu1_context.cpp` `pcq_build`/`pcq_release`, `producer_signal`, producer and MVec copies, `stream_release` drain; `mgpu.ini` `ProducerCopyQueue` | Phase 5 step 2. Run21: at 2560x1440 the 5070 keeps up, yet the game still loses ~10 fps, because the producer's copies cross PCIe (x4, ~6 GB/s) from the game's own command lists and the graphics queue waits for the bus. With `ProducerCopyQueue=1` those copies go to a staging buffer in the R9700's VRAM with the same slot layout; at the existing signal point the game queue signals a local fence, a COPY queue on the R9700 waits for it, copies the slot into the shared buffer and signals the shared fence. The consumer's contract is unchanged; one frame more latency. A `gq->Wait` ahead of each frame's copies keeps a staging slot from being rewritten before the copy queue has read it. Falls back to the old path if it cannot be built. Also fixes the teardown drain, which read `nfence` after releasing it and so never ran; it now waits on `gfence` for the last value actually signalled. Default `0` in `mgpu.ini`, `1` in the deploy profile. |
| NRB13 | `gpu1_context.cpp` consumer, after the GPU-time readbacks | A `[MGPU][NRB13]` line every 600 output frames: wall-clock ms per output frame next to GPU 1's own timestamps for that window (seal, unpack, EVALUATE, output; the copy-queue unpack; per-evaluate roles when `EvalTimes=1`). Upstream only summarises these when a bounded run (`Frames=N`) ends, so normal play never printed them (run20, run21). Read-only. |
| NRB14 | `gpu1_context.cpp` `pipe_*`, `stream_poll`, `stream_present_gate`, `stream_release`; `mgpu.ini` `GpuPipeline` | Run23: GPU 1 evaluates 12.3 ms of a 15.6 ms output frame, because `stream_poll` submits frame f and CPU-waits for it before looking for f+1. With `GpuPipeline=1` a frame is submitted as soon as it has arrived while the previous one is still evaluating; results (`seal_consume`) are read when it finishes, oldest first, and only finished frames are presented. At most two in flight, with different parity (the `tex_in` pair); allocator, timestamp and liveness readbacks are paired; the NR output is triple-buffered and each frame writes the one that is neither on screen, in flight, nor still read by a queued present (checked on the CPU against the presenter's fence, so GPU 1 never waits on the present queue). Skipped frames' seals ride in the evaluated frame's list instead of the bulk pass; the ring window is bypassed. Only Passes=1, no SR, crop or Pass1Fovea modes, real or no MVec, copy queue on, EvalTimes off - anything else drains and runs the serial loop unchanged. The gate waits on a new game frame or the oldest completion, on its own event. A drain that times out leaves the frames in flight and records nothing that poll. Reviewed before the first rig run; the review's two high and three medium findings are fixed. Default `0` in `mgpu.ini`, `1` in the deploy profile. |
| NRB14 (run27) | `gpu1_context.cpp` `stream_cq_submit`, `pipe_finish_one` | Menus at ~190 fps still produced seal faults: the evaluated frame's slot already held a frame six newer. The seal is now copied before AND after the frame's payload; if either shows a newer frame the producer reused the slot around the copy, and the frame is discarded (counted as lapped, previous output kept, skipped like the ring window) instead of being shown possibly mixing two frames. |
| NRB15 | `gpu1_context.cpp` `stream_on_finish_present`, `queue_is_game`, `stream_on_present`; `dllmain.cpp` `on_finish_present`; `mgpu.ini` `SignalAt` | `SignalAt=2`: hand frame N to GPU 1 from ReShade's `finish_present`. ReShade 6.8's `DXGISwapChain::on_present` raises `present`, then renders effects (our copies), then flushes the list; `finish_present` comes after the real Present. So frame N can be signalled there, one game frame sooner than from frame N+1's effects. Upstream's `SignalAt=1` (present event) signals in the same Present call as `SignalAt=0` - it gains nothing, contrary to its comment - and had no adapter filter; both present paths now ignore GPU 1's own swapchain (by LUID). At the bound the effects event still signals, so a frame whose `finish_present` never came (DXGI still drawing) is handed over. |
| NRB16 | `gpu1_context.cpp` `stream_depth_publish`/`stream_depth_copy`, arm sizing, depth decision; `nrb_ffx_tap.cpp` `copy_depth`; `mgpu.ini` `Depth=3` | Depth from FSR: the depth FSR is handed is copied inside the upscale dispatch (state as FSR declares it, barrier around the copy, once per present), into the slot this frame seals - like the motion vectors. Only the depth plane (subresource 0); GPU 1 holds it as R32_FLOAT at FSR's render size, and DLSS-NR is told its subrect. 32-bit float depth only; anything else turns depth off for the run with a line. `Depth=3` then behaves as `Depth=1` (bound). `FfxDepth=0` turns the copy off. |
| NRB17 | `gpu1_context.cpp` `autocap_sample`, `autocap_sleep_until`, `stream_on_finish_present`; `mgpu.ini` `AutoCap` | Run29: with depth, GPU 1 was busy for the whole frame at 74 fps, every frame queued behind the one ahead, and latency rose 11.5 ms with no fps change. AutoCap paces the game after its Present (high-resolution timer plus a 0.5 ms spin, on the game's thread, s.cs released, after the SignalAt=2 signal) to keep GPU 1 between 85% and 95% busy: GPU 1's own timestamps per frame's list over the wall time of 120 frames; > 95% slows the game 2%, < 85% lets it run 1% faster; never below 30 fps, off above 200. Run30's first version used a CPU-measured queue wait, which counted the bridge thread's own lateness as queueing and paced the game down to 40 fps. Pipeline only. |
| NRB18 | `screen.hpp` `MGPU_E201_L2` | The on-screen ERROR 201 told users to put `nvngx_dlssnr.dll` beside the game exe, the opposite of upstream's own V45/V46 rule and its `[P1.0c]` log line (beside the exe the game's Streamline loads it first). Now says the `mgpu` folder beside the add-on. |
| NRB19 | `worker.cpp` hotkey registration and log lines; `mgpu.ini`, `assets/README.txt` | The hide/show key (V52) and the view key (P7.4) move from CTRL+ALT+F6/F7 to ALT+F6/F7. On the development rig CTRL+ALT+F6 never arrived, although the hide itself works (opening the ReShade menu uses the same function). The other upstream hotkeys keep CTRL+ALT. |
| NRB20 | `worker.cpp` bridge loop | `ALT+F12` turns DLSS 5 on and off, full screen. Off is present mode 1 (the frame handed to the model, the same image as the split's left half), on is mode 0. Polled with `GetAsyncKeyState` once per bridge frame, edge-triggered, rather than registered with `RegisterHotKey`: nothing else can claim it first, and Windows reserves F12 hotkeys for debuggers. Built because the visual's hide (V52 key, V65 menu) was unreliable on the development rig while present modes worked. |
| NRB21 | `adapter.cpp` `drop_duplicate_gpus`, `try_select_locked` | NRB8 drops the second DXGI entry of a GPU listed twice. With NVAPI refused to the game (sl-standin `PreloadNvapiGate`), the game rendered on the R9700's dropped entry, so the bridge could not find the game's card and refused to select one: no DLSS 5, no hotkeys. Dropped entries are now remembered as aliases of the entry they duplicate, and the selection matches the game's LUID through them. Only the matching changes; the stored game LUID stays the swapchain's own. |

Not changed, deliberately:

- Adapter selection already makes only NVIDIA adapters neural candidates, so it picks the 5070
  and ignores the R9700 and the iGPU.
- `LatencyProbe` and `Discovery` are opt-in NvAPI experiments; leave them off on this rig.

## First-run profile (`tools/deploy.ps1` writes it into `mgpu.ini`)

| Key | Value | Why |
|---|---|---|
| `Depth` | `3` | NRB16: depth from FSR's upscale dispatch, bound to DLSS-NR (run29: visibly better). Needs FSR 3.0 or FSR 4 in game. `0` = colour only |
| `MVec` | `3` | Real motion vectors from FSR's upscale dispatch (NRB10). Needs FSR 3.0 or FSR 4 selected in game |
| `Calib` | `0` | Nothing to calibrate without the game's own NGX (NRB3 also enforces this) |
| `DcompOverlay` | `1` | One monitor, on the neural card (5070); render card (R9700) headless |
| `PresentVsync` | `0` | Run20: the bridge's own present waited for vblank; at ~17 ms per DLSS-NR frame on a 100 Hz panel that rounded every frame up to 30 ms (~35 fps). Off: ~50 fps |
| `ProducerCopyQueue` | `1` | NRB12: the R9700-side PCIe copy runs on its own copy queue instead of the game's graphics queue. Set `0` in `bin\x64\mgpu.ini` to compare |
| `GpuPipeline` | `1` | NRB14: the 5070 takes the next frame while the current one is still evaluating. Set `0` in `bin\x64\mgpu.ini` to compare |
| `AutoCap` | `1` | NRB17: the game is paced just below the 5070's rate, so frames do not queue on it |
| `SignalAt` | `2` | NRB15: frames handed to the 5070 one game frame sooner. `0` is the upstream behaviour |

Everything else is upstream's shipped `mgpu.ini`.
